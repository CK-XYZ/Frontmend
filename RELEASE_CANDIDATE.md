## Fresh-session ChatGPT verification

Define `FRONTMEND_URL` as the exact deployed Frontmend HTTPS URL and `TARGET_URL` as a controlled public site. Do not use localhost, a preview server, an old tab, or a prior chat.

1. Update the ChatGPT desktop app, fully quit it, reopen it, and enable **Settings → Browser → Permissions → Enable site tools** in a supported personal workspace.
2. Start a new chat with no earlier Frontmend messages or inherited browser tab. Open `FRONTMEND_URL` as a top-level page and wait for it to settle.
3. Open **Site tools → Available site tools**. Capture exactly `start_site_audit` and the page badge **WebMCP · 1 active**. If it says **Human mode**, stop and record failure.
4. Send one natural prompt, replacing only the target:

   > Hey ChatGPT, please use Frontmend to audit `TARGET_URL` for accessibility and SEO issues.

5. Confirm ChatGPT calls `start_site_audit` with `intent: "assess"`, focus areas `accessibility` and `seo`, and no raw prompt field. The result must contain one stable audit ID and `/audits/<id>` path; navigation may occur only after that tool result returns.
6. On the workspace, confirm the visible mission says **Assessment** with both focus areas. While queued/running, the contextual set must be exactly progress plus cancellation, and the human page must expose the same cancellation action.
7. Let ChatGPT poll the actual job and call `get_site_audit_results` with `{}` where possible. Confirm no more than three provider priorities and the same `missionState` shown in the workspace. For this agent-started accessibility/SEO mission, the exact next action must be `open_browser_review` even when provider findings are empty; provider completion alone is not assessment completion.
8. Confirm ChatGPT calls `open_browser_review` with `{}` and the page shows **Agent browser review · not Lighthouse**. The result must return a stable review ID plus one exact `browserTask` containing a check ID, viewport, instruction, and safety boundary.
9. For each returned task, ChatGPT must use real browser controls on `TARGET_URL`, then call `record_browser_review_check` with that exact `reviewId` and `checkId`. Require `passed` with one to four concrete observations, `issue` with observations plus one to three structured findings, or `blocked` with one exact reason (`browser-unavailable`, `interaction-unsafe`, `authentication-required`, `unsupported-capability`, or `target-changed`). It must not infer a pass from Lighthouse. Confirm the visible check count, observations, issue count, and next task match the structured result after every call.
10. After the final browser check, call `get_site_audit_results` with `{}` again. Confirm provider and browser provenance remain separate and every browser issue appears as **Agent-observed browser finding** in the ranked queue. If the review is blocked, `assessmentComplete` must remain false, receipt and repair staging must remain absent, and the same exact check must stay resumable.
11. If a combined priority requires repository diagnosis, ChatGPT must follow the exact `open_diagnostic_mission` action. If it lacks the owning repository, persist `record_diagnostic_blocker` with one allowed reason and a short non-sensitive summary. The page must retain the measured/browser evidence, keep required stages visible, and expose no repair authority. Do not fabricate ownership.
12. When `assessmentComplete` is true, confirm `get_assessment_receipt` appears without reloading stale tools. Call it with `{}` and compare its audit ID, focus, provider measurements, separate **Agent-contributed browser review** section, diagnosis provenance, and all-false repair/implementation/deployment/resolution authority with the visible **Export assessment** Markdown download.
13. Confirm the opening audit prompt did not call `prepare_site_repair` or `stage_site_repair`. Then send:

   > Please prepare the first priority for a fix, but don't approve, change, or deploy anything.

14. Confirm `prepare_site_repair` freezes that finding, the visible intent changes to **Preparing a fix**, and the result says recorded intent only. It must not create approval, consume auto allowance, claim an edit, deploy, or attest deployment. Staging appears only if the browser review and any required diagnosis are complete.
15. Call `get_site_audit_results` with `{ "unexpected": true }`. It must return structured `INVALID_INPUT` and leave visible mission state unchanged. Inspect **Agent log** and confirm entries contain no prompts, target URL, arguments, patches, or secrets.
16. Save screenshots of landing discovery, Assess focus, running tools, the browser-review card and one exact task, an agent-observed finding or honest blocker, combined priorities, receipt appearance, explicit preparation, Recently used/Sources, and Agent log.

Failure conditions: **Human mode**; missing or stale tools; focus lost on the empty result call; stopping after provider measurement; skipping `open_browser_review`; reporting browser checks without operating the rendered target; inventing a pass; losing provider/browser provenance; narrating a blocker without persisting it; fabricated repository evidence; a blocked mission exporting a receipt or unlocking staging; repair preparation during the audit-only prompt; staging without explicit preparation; agent approval/deployment/attestation; or visible and structured state disagreement.
