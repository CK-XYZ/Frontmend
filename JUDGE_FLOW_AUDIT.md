# Frontmend judge-flow audit

Audited: 29–30 August 2026, Australia/Perth
Surfaces: historical user-run local Frontmend experience on port 3434; current public older-version baseline at `https://frontmend.test.knightware.xyz/`; current candidate static/contract review
Flow: first audit entry → contextual WebMCP handoff → provider evidence → agent browser review → repository diagnosis → human repair review → proof boundary

## Overall verdict

The current local candidate has a materially stronger WebMCP idea than the deployed baseline: Frontmend uses contextual tools to orchestrate an external agent's rendered-browser and repository capabilities while the page keeps durable evidence, ordering, provenance, and authority. The public older build still hides this story behind a small capability panel and can read as “start Lighthouse”; it must not be used as visual proof of the new candidate.

The winning judge path is now: one natural request starts public measurement, Frontmend then reveals one exact non-destructive browser check at a time, the agent contributes direct observations or an honest blocker, browser-only issues become reviewable priorities, and repository/repair/deployment authority remains visibly separated. This turns WebMCP registration into the mission protocol rather than a decorative command catalogue.

## Steps

1. **Start from the URL field — healthy.** One obvious task, a useful real-site shortcut, public-page disclosure, keyboard focus, and a single primary action. The resting hierarchy is calm and distinctive.
2. **Inspect contextual WebMCP — healthy.** The modal explains the one capability currently available and keeps human authority explicit. Its close control receives focus and the agent vocabulary remains secondary to plain-language titles.
3. **Read and extend completed evidence — healthy after repair.** The report clearly separates score, findings, evidence mode, target, and provenance. Schema 5 turns the fallback into a visible Document profile with HTML size, resource counts, origins, inline-code counts, and response-header signals while retaining the zero-viewport boundary. The report exposes bounded same-site paths as explicitly unvisited candidates; the retained parent job validates an exact observed path for either adapter, while each child visibly carries its bounded root and parent trail. A bounded site mission can also run up to three selected pages and group recurring rules without turning Frontmend into an open crawler.
4. **Contribute rendered-browser evidence — strong in contract/static QA, fresh visual proof pending.** Agent-started accessibility or SEO missions cannot complete from provider output alone. `open_browser_review` returns one ordered task; `record_browser_review_check` accepts a direct pass, issue, or bounded blocker. The dark **Agent browser review · not Lighthouse** card mirrors check progress, observations, blocker state, and the no-source/no-deploy boundary. Browser issues enter the existing ranked queue with agent provenance.
5. **Submit a repository mission — healthy in static and automated contract QA.** The mission rail assigns ownership, repository files and checks are bounded, and the visible operating policy offers explicit review or an exhaustible three-use low-risk HTML/CSS delegation. The persisted contract rejects agent-authored policy changes and keeps ineligible work in review. A fresh rendered/browser receipt for this candidate is still required before submission.
6. **Deploy and prove — intentionally gated.** This audit did not approve a plan, attest an external deployment, or claim a repair result. The visible flow correctly prevents those steps without a person and a real public change.

## UX and accessibility findings

- The original fallback canvas exposed accurate but visually thin evidence; the implemented Document profile resolves the largest demo-confidence issue.
- The landing statement about mobile and desktop describes Lighthouse capability, while fallback runs may measure zero viewports. The completed report now makes that distinction prominent; no stronger promise should be added without a reliable Lighthouse provider.
- The profile uses a named region and semantic `dl`, `dt`, and `dd` metrics. Provider text and exported Markdown remain bounded and escaped.
- Lighthouse-scale evidence now distinguishes the full measured failure total from the bounded ten-item detail queue and states how many lower-priority details were omitted; all rule outcomes remain structured for agents and exports.
- Route discovery retains only unique same-origin paths, removes query strings, rejects asset links, caps the visible list at eight, reports omissions, and never describes those paths as audited until a follow-up job completes.
- Route journeys stop after five linked audits, retain only bounded ancestor IDs and paths, and describe that lineage as provenance rather than whole-site coverage.
- Site explorations admit the full one-to-three-page batch atomically, preserve per-page failures and IDs, cap aggregated issues and occurrences, and keep selected-page coverage explicit in UI, JSON, and Markdown.
- Screenshot evidence confirms hierarchy and visible state only. Full screen-reader behavior, browser zoom reflow, production latency, and real assistive-technology output were not proven by this audit.
- The new browser-review contract deliberately makes the same boundary visible: it is a bounded agent-contributed rendered review, not a complete manual accessibility or expert SEO audit.
